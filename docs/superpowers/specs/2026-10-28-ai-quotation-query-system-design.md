# AI 对话式报价查询系统 · 设计文档

- 日期：2026-10-28
- 状态：已与用户逐节确认，待最终审阅
- 数据目录：`d:\Projects\COMAU`（BAIC BE13/BE22、Tesla R05 两个项目）

## 1. 背景与可行性结论

### 1.1 现状数据盘点

| 类型 | 数量 | 说明 |
|---|---|---|
| .msg 供应商回复邮件 | 44 | 含发件人/日期/正文（商务条款，如"电汇价，承兑需重议"）/附件 |
| .xlsx 询价清单与报价单 | 19 | 询价清单结构规整；各供应商报价格式完全不同 |
| .pdf 报价单 | 28 | 多为文本层 PDF |
| .png 价格截图 | 14 | 需视觉模型识别 |
| .doc / .pptx | 各 1 | 少量 |

### 1.2 可行性结论：可行

已验证：
- `extract-msg` 可完整解析 .msg（主题/发件人/日期/正文/附件清单）
- `openpyxl` 可读取询价清单核心表 `Inquiry table`（Remark/Product/Commodity/Category/Vendor list/Qty1-10/Unit Price）
- 询价清单自带品类体系（DATA 表：名称 → Commodity Cluster/Buyer/Category），可直接作为标准分类基准
- 各供应商报价格式异构（KUKA、盛允、冠宇三套格式完全不同），正是 LLM 结构化抽取的适用场景

### 1.3 方案选型（已确认）

选定 **方案 A：结构化知识库为主 + 语义匹配辅助**。备选方案 B（纯向量 RAG）对数值聚合查询和报价草稿生成能力弱；方案 C（对话时现场解析）慢、贵、结果不稳定，均不采用。

## 2. 需求与已确认决策

| 决策点 | 结论 |
|---|---|
| 使用者/环境 | 个人本地使用（Windows），数据不出本机（LLM 调用除外） |
| LLM | 云端 API（OpenAI 兼容接口，需带视觉能力） |
| 核心流程 | 清单导入匹配 + 对话式查询并重 |
| 数据更新 | 手动批量导入（新项目文件夹放入后跑一条命令） |
| 界面 | 本地 Web 界面（FastAPI + 浏览器） |

**目标**：
1. 把现有 2 个项目约 105 个文件的历史报价整理为可检索的标准化数据库
2. 对话式查询历史报价（按品类/供应商/项目/时间），答案带溯源
3. 新项目上传询价清单，逐行匹配历史报价，生成报价建议草稿 Excel

**非目标**：
- 不做自动定价决策（建议仅供参考，最终价格由人判断）
- 不做自动监听邮箱/文件夹
- 不做多用户权限体系

## 3. 总体架构

四层：数据源 → 建库管道 → SQLite 知识库 → 应用（对话查询 / 清单匹配 / 草稿生成）。

```
.msg / .xlsx / .pdf / .png
        │
文件解析器 (extract-msg · openpyxl · pymupdf · 视觉模型)
        │
LLM 结构化抽取（任意格式 → 统一记录，JSON 校验 + 置信度评分）
        │
SQLite 报价知识库（报价明细 · 供应商 · 品类 · 项目 · 向量索引 · 溯源）
        │
对话式查询  |  清单导入匹配  |  报价草稿生成(Excel)
```

## 4. 数据模型（SQLite）

### 4.1 quote_items（核心表，每行一条历史价格）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| project_code | TEXT | 如 BAIC_BE22、TESLA_R05 |
| supplier | TEXT | 供应商名（盛允、KUKA、冠宇…） |
| category | TEXT | 品类，对齐询价清单 DATA 表分类体系（7-Axis、Roller bed、Arc Welding…） |
| product_name | TEXT | 设备名称 |
| spec | TEXT | 规格/描述（长度、配置、含否校直等） |
| brand / model | TEXT | 品牌 / 型号 |
| qty / unit | REAL / TEXT | 数量 / 单位 |
| unit_price | REAL | 单价 |
| currency | TEXT | CNY / USD |
| tax_included | INTEGER | 含税否（含税/未税必须识别，供应商报价两种都有） |
| price_status | TEXT | 成交价 / 本次报价 / 历史报价 / 预估价（沿用询价清单 Remark 体系） |
| quote_date | TEXT | 报价日期（取邮件日期或文件名日期） |
| terms | TEXT | 商务条款（从邮件正文抽取，如付款方式、返点、有效期） |
| source_file_id | INTEGER FK | 溯源到 source_files |
| source_location | TEXT | sheet+行号 或 PDF 页码 |
| confidence | REAL | 抽取置信度 0-1，低于阈值进人工复核队列 |
| needs_review | INTEGER | 校验警告标记 |
| created_at / updated_at | TEXT | |

### 4.2 辅助表

- **source_files**：文件路径、内容哈希（幂等去重）、类型、关联 project；邮件额外存主题/发件人/日期/正文摘要
- **suppliers**：供应商 ↔ 品牌（从邮件域名、报价单自动积累）
- **inquiry_matches**：新清单行与 quote_items 的匹配结果（匹配档位、参考记录 id 列表、建议价、差异说明）
- **conversations**：对话历史（本地存储）

## 5. 建库管道（脚本，可重复运行）

```
扫描项目目录 → 按类型解析 → LLM 抽取(JSON schema) → 自动校验 → 入库
                                                   ↘ 低置信度 → 人工复核清单(CSV)
```

- **解析**：.msg 用 extract-msg（正文+附件）；.xlsx 用 openpyxl 全 sheet 扫描；.pdf 用 pymupdf 提文本；.png/.doc/.pptx 及扫描版 PDF 走视觉模型
- **抽取**：每个文件的内容（表格序列化或 PDF 文本）发给 LLM，要求按 quote_items 字段返回 JSON；邮件正文单独抽取商务条款并与其附件报价关联为同一批次
- **校验**：价格必须为数字；币种/含税必须识别；数量×单价 与报价单小计交叉核对（偏差 >5% 标警告仍入库）
- **幂等**：按文件路径+内容哈希去重，重跑只处理变化文件；断点续跑（API 失败跳过并在报告中列出）
- **规模预估**：约 105 文件，1-2 小时跑完，API 成本约几十元人民币

## 6. 对话式查询（两段式检索）

1. **意图解析**：LLM 将问题转为结构化查询条件（品类/供应商/项目/时间/价格状态）
2. **SQL 检索**：固定查询工具层查 quote_items（精确，支持计数、最值、均值等聚合）；LLM 不直接生成任意 SQL
3. **语义兜底**：术语不一致时（"七轴" vs "机器人第七轴"）用 embedding 近邻补充召回
4. **LLM 汇总**：将命中记录（含溯源信息）交给 LLM 组织回答；**每个价格必须标注来源文件**，无依据不编造

## 7. 清单导入与报价草稿

```
上传新询价清单 xlsx → 逐行解析 → 匹配历史报价 → 生成建议 → 导出 Excel
```

匹配四档：

| 档位 | 条件 | 建议价 |
|---|---|---|
| 精确匹配 | 同品类+同品牌+规格相近 | 直接引用（优先成交价） |
| 相似匹配 | 同品类，品牌/规格有差异 | 参考价 + 差异点说明 |
| 弱匹配 | 仅品类相同 | 历史区间（min/中位/max） |
| 无匹配 | 无历史数据 | 留空待询价 |

导出 Excel = 原清单列 + 建议价 + 匹配档位 + 参考依据（项目/供应商/日期/溯源）+ 人工确认标记。

## 8. Web UI（本地 FastAPI + 单页原生 HTML/JS）

- **对话区**：问答历史；价格数字带溯源按钮（弹窗显示源文件路径/邮件主题/行号）
- **清单工作台**：上传 → 匹配进度 → 预览表格（可按档位筛选）→ 下载草稿
- **数据管理**：已入库项目/文件列表；低置信度与校验警告清单，支持人工修正后回写

## 9. 错误处理

- LLM JSON 解析失败：带错误重试 2 次 → 降级人工复核队列
- 抽取校验警告：入库但标记 needs_review，UI 中高亮
- API Key/网络/限额：明确报错；断点续跑；已入库文件跳过
- 查询无结果：明确说"库中无数据"，不编造

## 10. 测试与验收

- **抽取质量**：抽 30 条人工核对，全字段准确率 ≥90%，价格/数量/供应商三关键字段 ≥95%
- **查询正确性**：预置 10 个典型问题（如"BE22 七轴各家报价对比"）验证与库内数据一致
- **清单匹配回测**：用 BAIC BE22 自身清单行匹配库内其对应报价，验证召回
- 管道幂等性：重复运行不产生重复记录

## 11. 技术栈

Python 3.14 + SQLite + FastAPI + extract-msg / openpyxl / pymupdf + OpenAI 兼容云端 API（需视觉能力：qwen-vl / glm-4v / gpt-4o 等）+ 原生前端（无构建工具）。

## 12. 风险与开放问题

| 项 | 说明 | 处理 |
|---|---|---|
| 视觉模型选型 | 取决于用户手上的 API Key | 用 OpenAI 兼容抽象层，模型名写在配置文件，可随时切换 |
| 扫描版 PDF 识别质量 | 若 PDF 无文本层需视觉模型，价格数字识别可能有误 | 抽样核对 + 置信度阈值 + 人工复核队列 |
| 供应商命名归一 | 同一供应商不同写法（盛允/允盛） | LLM 抽取时给已有供应商列表做归一 |
| 品类体系扩展 | 新项目可能出现新品类 | category 表开放追加，抽取时对齐最近似品类 |
